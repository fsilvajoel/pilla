# E9: cadastro de pessoas de ponta a ponta

Pedido do Joel em 19/11/2026: o cadastro de pessoas tem que funcionar de ponta a ponta. Isso inclui telas visuais com
shadcn/ui e Tailwind (base clara, verde claro), rotas da API funcionando e dados vindos do banco de verdade. A épica
cobre **só pessoas**. Todo componente que puder ser reaproveitado fica num diretório próprio, e usamos os
componentes prontos do shadcn sempre que possível. Variantes novas são planejadas, não improvisadas.

Fluxo: cada feature passa pelo [workflow feature do harness Ada](../../../harness-ada/workflow/feature.md), na
ordem plan → refinamento → tests → revisão dos testes → implement → mutação/e2e → revisão final → fechamento.
Os cartões ficam em [E9.yaml](E9.yaml) e são esqueletos. O planner detalha `done`, `hints` e `readFirst` no
`plano.md` de cada feature.

| RF | O quê | Entra na E9 |
|---|---|---|
| RF-01 | cadastrar e editar pessoa | sim |
| RF-02 | endereços (um principal) e chaves PIX (uma principal) | sim |

Fora da E9: login (ADR-0011), exclusão de pessoa (não existe RF para isso) e o portal do cliente.

## Decisões (19/11; o Joel delegou: a opção mais simples e funcional)

- **D1 Backend:** NestJS (RFC-003 §4.2), base `/api/v1`, corpo e resposta validados com os Zod de
  `@pilla/schemas` só na borda HTTP (decisões de 19/11 §4). Erros em `application/problem+json` (RFC-004 §2).
- **D2 Banco de desenvolvimento:** o ambiente de desenvolvimento ainda não tem Docker. Instalamos Docker e criamos `infra/docker-compose.yml` com
  PostgreSQL (RFC-003 §4.8), migrations aplicadas por script e um seed mínimo. Os testes continuam com PGlite.
- **D3 Sem login nesta épica:** as rotas de pessoas ficam abertas. A API escuta só em `127.0.0.1` e é chamada
  apenas pelo servidor do Next. O guard do ADMIN entra na épica de acesso e protege as rotas sem mudar o contrato.
- **D4 Web ↔ API:** leitura por Server Components e escrita por Server Actions com `revalidatePath` (ADR-0013).
  O navegador nunca chama a API direto. A URL da API vem de `PILLA_API_URL` (`.env`).
- **D5 Paleta:** base clara (fundo branco e cinza muito claro) com verde claro de destaque. Os tokens do shadcn
  (`--primary`, `--accent`, `--ring`, `--sidebar-*` etc.) ficam em `app/globals.css`, com contraste AA para texto
  sobre o primário. No MVP há só o tema claro.
- **D6 Componentes:**
  - `apps/web/components/ui/`: primitivos do shadcn instalados pela CLI (`pnpm dlx shadcn@latest add …`). Não são
    editados à mão, a não ser para acrescentar uma variante planejada.
  - `apps/web/components/shared/`: compostos reaproveitáveis (cabeçalho de página, estado vazio, campo de
    formulário, tabela de dados, diálogo de confirmação, selo de status, casca do ADMIN).
  - `apps/web/components/people/`: componentes de domínio de pessoas.
- **D7 Ficha:** mostra o que já existe em `people` (dados, endereços, PIX, quem indicou e indicados) e um bloco
  "Contratos" vazio ("Nenhum contrato"). O resumo de contratos entra quando houver a consulta pública de
  `lending` (RFC-004 `GET /people/{id}`).
- **D8 CPF repetido:** a RFC-004 §6 não tem código para esse caso. Entra o **409 `CPF_ALREADY_REGISTERED`**, com o
  texto "Já existe uma pessoa com este CPF.", e a RFC-004 §6 é ajustada no cartão da API.
- **D9 Edição concorrente:** `PATCH /people/{id}` exige `If-Match` com a `version` e responde 409
  `VERSION_CONFLICT` quando ela está desatualizada (RFC-004 §2 e §6). A coluna `version` já existe.
- **D10 Skill do shadcn:** a skill oficial (`shadcn/ui`) já está no harness (`skill/shadcn`, junto com
  `tailwind-css`). O harness injeta as duas em todo cartão de tela, então não há instalação nova. Para atualizar
  a skill, roda-se `npx skills add shadcn/ui` no diretório de skills do harness, numa tarefa separada.
