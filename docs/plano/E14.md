# E14: Login e sessão do ADMIN

Planejada em 23/11 no formato da E12 e da E13. Cartões em `docs/plano/E14.yaml`; um `plano.md` por feature em
`docs/plano/E14-F01/` a `E14-F07/`.

Fluxo de cada feature: `../../../harness-ada/workflow/feature.md` (plan, refinamento, testes, revisão dos testes,
implementação, mutação/e2e, revisão final, fechamento).

Base: [ADR-0007](../adr/0007-controle-de-acesso-por-papeis.md) (papéis num lugar só),
[ADR-0011](../adr/0011-autenticacao-cpf-senha-sessao.md) (login e senha, argon2id, sessão no servidor, cookie `httpOnly` + `Secure` +
`SameSite=Lax`, sem JWT, sem 2º fator), PRD-001 (RN-A01, RN-A03, RN-A05), RFC-003 §4.5, RFC-004 §3 e §6, RFC-005
(schema `access`, já criado em `apps/api/src/access/infra/schema.ts`).

## Escopo (PRD-001)

| Regra | O quê | Entra |
|---|---|---|
| RN-A05 | ADMIN acessa com login e senha, sem 2º fator | Sim: `POST /auth/admin/login`, `POST /auth/admin/logout`, `GET /auth/me` (F01, F02) e tela `/login` (F06) |
| RN-A01 | Dois papéis, ADMIN e CLIENTE | Parcial: o guard global (F03) exige ADMIN em toda rota administrativa. O papel CLIENTE e o portal ficam com a entrega do portal |
| RN-A03 | Toda ação de ADMIN que altera dados é auditada | Sim: o ator da auditoria e o `created_by`/`confirmed_by`/etc. passam a ser o ADMIN da sessão, no lugar do ator provisório (F04) |
| RF-60 | ADMIN habilita ou desabilita o portal de um cliente | Não: vai com o portal (D10, pendência de PM) |
| — | Primeiro ADMIN | Sim: script de seed sem segredo no git (F05). Não há tela de cadastro de ADMIN no MVP (D9) |

Fora: portal do cliente (RN-A02, RN-A04, RF-61 a RF-63, `POST /portal/session`, `access_logs`), troca e recuperação de
senha pela tela, gestão de vários ADMINs pela tela, 2º fator (ADR-0011).

## Decisões

- **D1. Módulo e fronteiras.** Tudo de autenticação mora em `apps/api/src/access/{domain,application,infra,http,public}`
  (M6 Acesso, ADR-0007). Os outros módulos não importam `access`: o ator da requisição é um tipo do core,
  `RequestActor = { type: "ADMIN"; adminUserId: string; ip: string | null }` em `core/public/actor.ts`, lido no controller
  pelo decorator `@CurrentActor()` de `core/http`. A permissão por papel fica num lugar só: o guard de `access/http`.
- **D2. Senha.** `argon2` (já liberado em `docs/travas.md`), variante argon2id com os parâmetros do OWASP
  (memória 19 MiB, 2 iterações, paralelismo 1), constantes em `access/domain/password.ts`. A senha nunca vai para log,
  erro ou resposta. Usuário inexistente ou inativo também roda um `verify` contra um hash fixo, para o tempo de
  resposta não revelar quais usuários existem.
- **D3. Token e sessão.** Token aleatório de 32 bytes (`crypto.randomBytes`), em base64url no cookie. A tabela
  `access.sessions` guarda só o SHA-256 em hex como `id` (char 64), nunca o token. `role` ADMIN, `admin_user_id`,
  `ip`, `created_at`, `last_seen_at`, `expires_at`. Expira por inatividade (2 h desde `last_seen_at`) ou pelo teto
  absoluto (12 h desde `created_at`, gravado em `expires_at`); valores padrão da pendência de PM E14-T03, constantes no
  código, sem variável de ambiente. `last_seen_at` é atualizado no máximo uma vez por minuto. Sessão expirada é apagada
  quando aparece; sem rotina de limpeza.
- **D4. Cookie.** Nome `pilla_session`; `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, sem `Max-Age` próprio (a
  validade é a do servidor). A API lê o cookie direto do cabeçalho `Cookie` (sem `cookie-parser`, que não está na lista
  de dependências). Como o navegador só fala com o Next (ADR-0013), o cookie que o navegador guarda é o do Next, com os
  mesmos atributos; o servidor do Next repassa o valor à API em cada chamada (D8).
- **D5. Contrato.** Prefixo `/api/v1`, Zod de `@pilla/schemas` na borda, erros problem+json da RFC-004 §6.
  - `POST /auth/admin/login` com `adminLoginRequest` (já existe em `packages/schemas/src/api/access/admin-login.ts`):
    200 com `adminMeResponse` e `Set-Cookie`; 401 `UNAUTHENTICATED` com a mesma mensagem para usuário inexistente,
    inativo ou senha errada ("Usuário ou senha inválidos."); 400 `VALIDATION_FAILED`; 429 `TOO_MANY_REQUESTS`.
    Atualiza `admin_users.last_login_at`.
  - `POST /auth/admin/logout`: 204, apaga a linha da sessão e devolve o cookie vencido; sem sessão também responde 204.
  - `GET /auth/me`: 200 `adminMeResponse = { id, username, role: "ADMIN" }`; 401 sem sessão válida.
  - Login e logout não são "alteração de dados" (RN-A03): não gravam `audit_log`.
- **D6. Limite de tentativas.** `@nestjs/throttler` (liberado) só na rota de login: 5 tentativas por minuto por IP;
  a 6ª responde 429 `TOO_MANY_REQUESTS` (padrão da pendência E14-T03). O filtro de problem+json traduz a exceção do
  throttler. O contador fica em memória (uma instância da API no MVP).
- **D7. Guard global.** `AdminSessionGuard` registrado como `APP_GUARD` no `AppModule`: toda rota exige sessão ADMIN
  válida, salvo as marcadas com `@Public()` (decorator de `core/http`): `GET /health`, a rota do OpenAPI e
  `POST /auth/admin/login`. Sem sessão: 401 `UNAUTHENTICATED`; sessão de outro papel (CLIENT): 403 `FORBIDDEN`. O guard
  põe o `RequestActor` na requisição. IP: a API escuta só em 127.0.0.1 e confia em `X-Forwarded-For` apenas quando a
  conexão vem do loopback (o servidor do Next); senão usa o IP da conexão.
- **D8. Testes HTTP existentes.** `createTestApp` ganha o parâmetro opcional `actor`: por padrão injeta
  `TEST_ADMIN_ACTOR` (UUID fixo em `core/http/test-actor.ts`) sem passar pelo guard, para os testes de cada módulo
  seguirem focados no módulo. O guard real e as rotas de auth são testados em `access/http` com o guard ligado, e um
  teste do `AppModule` confere que rota sem `@Public()` devolve 401 sem cookie.
- **D9. Primeiro ADMIN.** Script `pnpm --filter @pilla/api db:seed-admin -- --username <nome>`: lê a senha do
  terminal (oculta, digitada duas vezes) ou da entrada padrão quando não é terminal; nenhuma senha em arquivo,
  variável de ambiente ou git; nenhuma variável nova no `.env.example`. Recusa host de banco fora de localhost (igual ao
  `db:seed`) e senha fora da política (12 a 200 caracteres, padrão da pendência E14-T09). Se o usuário já existe, só
  troca o hash da senha e reativa (serve de "recuperar senha" no MVP). Sem tela de cadastro de ADMIN.
- **D10. RF-60 fora.** `PUT /portal-access/{personId}` fica com a entrega do portal, que é quem usa
  `access.portal_access` (pendência E14 esqueleto). A E14 só garante que `portal_access.enabled_by` terá um ADMIN real
  para apontar.
- **D11. Ator real (RN-A03).** Somem `PROVISIONAL_ACTOR_ID` e todo `actorId: null` de ação de ADMIN: em payments
  (`created_by`, `confirmed_by`, `rejected_by`, `reversed_by` e auditoria), lending (auditoria dos contratos,
  `mark-loan-paid-off`, `reopen-loan`) e `default_terms` (`created_by` passa a ser o ADMIN da sessão, encerrando a
  regra provisória registrada em `pendencias-pm.md`, "E13-F01: created_by do default_terms"). O `ip` da auditoria
  passa a ser o da requisição. Eventos automáticos continuam com `SYSTEM_ACTOR_ID` (E12 D3). Se os lançamentos manuais
  da tesouraria (E12-F02) já estiverem na `main`, entram no mesmo cartão.
- **D12. Web.** Tela pública `/login` (fora do grupo `(admin)`), formulário com server action que chama
  `POST /auth/admin/login` repassando o IP do cliente em `X-Forwarded-For`, copia o token do `Set-Cookie` da API para o
  cookie do Next (D4) e redireciona para `/` (ou para a rota de origem, só caminhos internos). O `layout.tsx` de
  `(admin)` chama `GET /auth/me` e redireciona para `/login` sem sessão; `lib/api/client.ts` repassa o cookie em toda
  chamada e, ao receber 401, redireciona para `/login`. Botão "Sair" no `AdminShell` (server action de logout).
  **D12 reaberta (23/11, ordem do Joel): o `apps/web/proxy.ts` (Next 16) passa a existir.** Sem o cookie `pilla_session`
  ele redireciona rota de admin para `/login?next=<caminho e query originais>` e deixa passar `/login`, `/portal*`,
  `_next` e arquivos estáticos. É só navegação: a checagem que vale continua sendo a do servidor da API, e o layout
  `(admin)` segue validando com `GET /auth/me`. Telas sem teste unitário nesta fase (E13 D10); o `proxy.ts` tem teste
  unitário; a cobertura de tela é o e2e (F07).
- **D14. Autenticação desligável em desenvolvimento.** `PILLA_AUTH_ENFORCED` (padrão `true`; ausente ou qualquer valor
  diferente de `false` mantém a exigência). Com `false`: o `AdminSessionGuard` libera, usa a sessão válida se houver
  ou o admin ativo mais antigo do banco como ator (sem admin ativo, 401 com mensagem pedindo `db:seed-admin`),
  `/auth/me` faz o mesmo, o `proxy.ts` e o layout `(admin)` não redirecionam e o `apiFetch` não redireciona em 401.
  API e web registram WARN "autenticação DESLIGADA, só desenvolvimento" na subida. Nunca ligar fora do dev.
- **D13. E2E.** Um `globalSetup` do Playwright cria um ADMIN de teste pelo `db:seed-admin` com senha aleatória gerada
  na hora, faz login uma vez e salva o `storageState`; os e2e existentes passam a usá-lo. Nenhuma senha fixa no código.

## Pré-requisitos

- Schema `access` migrado (`access.admin_users`, `access.sessions`) e seus testes de tabela verdes (já na `main`).
- `adminLoginRequest` em `@pilla/schemas` (E2-T14, já na `main`).
- `argon2` e `@nestjs/throttler` entram no `apps/api/package.json` pelos cartões de implementação (já liberados em
  `docs/travas.md`).
